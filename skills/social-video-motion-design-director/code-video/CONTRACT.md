# Code-video rendering contract

## Choose a mode before choosing files

A request can ask for (A) a human-readable plan, (B) a machine-readable handoff, (C) source code, (D) rendering/encoding, or a combination. A script-only request does not authorize B–D. State the requested mode, engine/profile and exact deliverables before work. Ask about material choices; do not invoke a renderer, install software, replace existing files, publish, or use unlicensed assets without authorization. A requested video build may authorize implementation and rendering within the brief. Reports must distinguish planned code, source written, frame rendered, encoded output, and actual playback.

For a **detailed code-based production handoff or build**, supply a versioned machine-readable manifest in addition to the narrative storyboard unless the user explicitly requests prose only. Name its path, schema/profile, authoritative status and how the renderer consumes it. It controls machine-readable visual/timing values; human-readable narrative, VO and documentation explain intent but may not silently contradict it. Name separate authorities for VO, audio, captions and delivery configuration if they are not covered by the schema. Validate every dependent file and report provenance, approvals and untested fields. Do not make a speculative manifest appear approved. If unconfirmed settings block a final manifest, use percentages or provisional seconds; an assumed-fps example is allowed only when explicitly requested or useful and is labeled illustrative throughout. Ask before locking or rendering a materially different final format. Do not output numeric frame examples as confirmed.

Use the included **Director vector profile v1** below for a compatible 2D, primitive-based project. It is a deliberately small, executable reference—not a universal video format. For Remotion, Canvas, ffmpeg, 3D, images/video/audio, shaders, or another medium, explicitly choose an appropriate engine and versioned machine-readable contract, document its field meanings, asset boundaries, timing, mapping and validation, and provide the required tooling or mark it NOT CHECKED. Do not silently drop requested media or translate unsupported features into this profile. If no viable profile/tool can meet the brief, ask or provide only a clearly labeled plan.

## Portable deterministic rendering requirements

Specify a pure frame evaluation contract: visual state `frame(index, manifest, fixed assets, render configuration)` must not depend on prior frame evaluations, wall-clock time, network responses, playback state or unseeded randomness. Explicitly seed any random generator and derive values from stable identifiers/index rather than mutable shared state. Lock the renderer/runtime, assets, fonts and relevant settings. Decode media by explicit timestamp/frame where supported. Load fonts/assets before measuring or capture; a missing font is an error, not permission for silent fallback. For non-seekable physics or stateful systems, precompute/cache deterministic frame-addressable state and identify it as an input, or flag determinism NOT CHECKED.

Test same frame repeatedly and in different seek orders with fixed inputs; compare raw decoded pixels or explicitly scoped vector/state output, not only encoded-video bytes (encoders can include variable metadata). Record frames, environment and hashes/diffs. Select a representative set at minimum; broader claims remain PARTIAL until their full named scope is checked. Across operating systems, font shapers, codecs and GPU drivers, identical pixels are not assumed. For audio, specify sample rate, channels, offset and deterministic processing; do not claim audio is tested from visual-frame checks.

## Director vector profile v1

Machine-readable definition: [`manifest.schema.json`](manifest.schema.json). It uses JSON Schema draft 2020-12 plus semantic validation by `tools/vector_profile.py`; both are required. There are no implicit fields or extensions: unsupported features require a different, explicitly versioned contract. Validate the actual shipped file. Reject malformed JSON, duplicate object/scene/asset IDs, bad asset hashes/paths, unsupported version/type, inconsistent total, invalid visibility/animations, timeline gaps and overlaps, or unconfirmed production timing. The validator cannot verify user approval merely from a manifest string; cite and check actual approval separately.

- **Format and authority:** UTF-8 JSON. `schema_version` must equal `1.0.0`; `purpose` is `production` or `illustrative`. Reject duplicate JSON keys. Do not silently reinterpret another version: use a corresponding versioned schema/renderer and explicitly document any migration; preserve the original and validate/hash the migrated output. Treat the file's **actual bytes** as authoritative for this profile; changes require a new validation and checksum. Do not derive a byte hash from reserialized or embedded content. Follow `references/operating-contract.md` for file/block extraction, newline and SHA-256 comparison.
- **Timing:** FPS and duration are positive rational numerator/denominator values with `CONFIRMED`/`PROPOSED` and provenance. Production requires both confirmed; an illustrative manifest may use proposals and must never be presented as final. `total_frames = floor(duration*fps + 0.5)` using rational arithmetic. All scene and object visibility intervals are 0-based `[start,end)`; `end` is not visible. Scenes cover `[0,total_frames)` consecutively. A scene boundary is a hard cut only if the visual objects/animation actually make one: object visibility may span boundaries, and transitions can overlap through object visibility and animation even though scene ownership intervals do not overlap.
- **Canvas and space:** canvas width/height are output pixels; origin is top-left, x increases right, y increases down, viewport center is `(width/2,height/2)`. `camera.anchor` is an explicit point in pixels and may differ from that center. `camera.scale` is positive and `camera.offset` is in output pixels. For a world-space point after its object translation `p`, output point is `anchor + scale*(p-anchor) + offset`; screen-space objects ignore camera. Negative/off-canvas coordinates are permitted by schema but need explicit intentional-clipping treatment in QA. Use a different profile for rotation or a moving camera.
- **Primitive vocabulary:** `rect` uses top-left `x,y,width,height`; `circle` uses center `cx,cy` and `radius`; `line` uses endpoints `x1,y1,x2,y2`; `text` uses left-aligned alphabetic baseline `x,y`, a single line, `text`, explicit `font_asset`, and `font_size`. Each has an ID, `[start,end)` visibility, `world` or `screen`, integer `z`, paint/style and animations. Font is the only supported external asset in this profile; it must be explicitly allowed, included at a safe relative path under the manifest directory and hashed from its actual bytes. Empty allowed/assets lists mean no external assets. Text requires an asset ID. This profile alone cannot express audio, images, video, arbitrary SVG, shaders or textures—choose another documented profile when they are needed. This restriction is **not** a general prohibition across projects.
- **Paint and order:** solid `#RRGGBB` colors or null fill/stroke, nonnegative stroke width and opacity `0..1`. Background is opaque. Paint objects ascending by `(z, id)`; later objects appear on top. Strokes are centered on the shape. World-space geometry and strokes scale with camera; screen-space elements do not. The reference SVG serializer rounds output coordinates to six decimal places; do not round to integer pixels. An engine with other rounding/antialiasing must disclose it and measure its actual output. Intentional overlaps must be described and separately reviewed.
- **Animation:** `translate_x`, `translate_y`, and `opacity` are the only animated properties. Each event has absolute integer `start` and `end` **frame points**, both visible, with `start < end`; unlike visibility intervals, the value at `end` is the exact endpoint. Each property’s events must not overlap, including endpoints. No implicit delay: an event starting after visibility begins is delayed until that frame. Before the first event hold its `from`; between events and after the last hold the preceding `to`. If the next event's `from` differs, it jumps at that event's start. `linear` uses `t`; `smoothstep` uses `t*t*(3-2*t)`; `step` holds `from` until `end`; `t=(frame-start)/(end-start)`. For fading use an opacity event (e.g. `from:1,to:0`); no hidden `fade_out` behavior. No animations means translation zero and style opacity. Avoid overlapping fades/translation assumptions that are not encoded.
- **Fonts:** pin the actual font bytes/hash, renderer and shaping versions; prohibit silent fallback. Specify script/language, direction and text shaping in profiles that support them. Measure actual shaped text with the final renderer/font, including stroke/transform and caption panel. The reference SVG renderer only emits font declarations; it does **not** measure glyphs or guarantee the viewer supports the font. Character count is a planning heuristic, not geometry. Missing metrics or unsupported shaping is NOT CHECKED/NEEDS HUMAN REVIEW.

## Outputs and acceptance

For a compatible code-based handoff provide: `production-plan.md` (or equivalent); authoritative `visual-plan.json` validated against the selected versioned schema; any explicitly referenced, rights-cleared assets and their hashes; renderer source and dependency/version instructions **when code is requested**; and `review.md` with named checks, evidence, exact scope and outstanding risks. For a render request additionally provide actual frames/video and output metadata only after rendering; for revisions include a `revision-log.md` with before/after evidence. Add contact sheets or test reports when generated; don't claim they exist when they do not. Prose-only/script-only requests do not require these files. List missing outputs and stop any dependent final action when tools or approval are unavailable.

For real production, implement and report these named checks against actual transformed/rendered states where relevant: schema/timeline/assets; output canvas bounds and intentional clipping; protected text-to-text overlaps; text-in-rectangle and text-in-circle containment; connector endpoint/segment-to-node contact at both ends; each text/graphic foreground/background contrast pair; each caption line's shaped width and panel/safe-area fit; reading-hold durations; caption/VO timing; sampling of scene/cut/motion/cue boundaries; playback/audio; exact export metadata and placement preview. Record threshold, frames, objects, measurement source, failures and missing coverage. Human review handles intended overlaps, semantic meaning, animation quality and ambiguous contrast; pixel sampling or geometry alone is not accessibility certification. In each named scope FAIL if an observed required check fails, PARTIAL if only a subset of that scope was checked, NOT CHECKED if no relevant evidence, PASS only if the entire explicitly named scope passed. A broader review may be PARTIAL even if a narrow subcheck passes. No passing result may be implied for the whole output from examples or a few sampled frames.

The included `tools/qa.py` is a **small reference**, not that complete production harness: it validates schema/semantics/asset hashes, compares a few SVG frames in two orders, and checks analytic non-text shape bounds (all frames up to a limit). It treats any examined out-of-canvas box as a failure and has no intentional-clipping exception; adjudicate deliberate clipping separately. It cannot establish that a declared font is valid or actually loaded. It explicitly reports other categories NOT CHECKED and the overall review PARTIAL. `tools/measured_checks.py` evaluates explicitly supplied measurements for bounds, overlap, rectangular/circular containment, endpoint contact, contrast and caption-panel fit; it does not extract or authenticate those measurements from actual frames and does not verify scene or temporal coverage. Supply measurements from the actual renderer with frame IDs and evidence; convert stroke/outline/camera transforms into the measured geometry. Endpoint checks support edge contact only; a line deliberately extending inside a node requires the documented segment-boundary test separately. Tool output is only a math check of input observations, never proof of a complete render review.

For anti-patterns: do not invent facts, charts, statistics, testimonials, asset rights, checksums or test evidence; do not let decorative movement stand in for proof; do not represent a static hub as a network effect; do not equate sampled-frame success with all-frame success, a syntactically valid manifest with a visually correct video, or a video plan with an actual render. Maintain material qualifiers and mark modeled sequences as illustrative.

## Executable reference and golden fixture

The reference engine is `tools/vector_profile.py`: one frame in, deterministic UTF-8 SVG bytes out. It validates first and uses exclusive file creation unless `--force` is explicitly passed. It is not a video encoder or audio mixer. `examples/vector-example.json` is a synthetic **illustrative** 160×90, eight-frame, four-fps example, not a project recommendation. `examples/frame-0.svg` and `frame-7.svg` are checked-in expected SVG-byte outputs; `examples/SHA256SUMS` records the actual manifest and reference-output bytes. They are reference outputs for this engine and fixture, not universal pixel goldens: rasterization, fonts, playback, platform compliance and creative quality are untested. `examples/measurements-example.json` contains synthetic measurement inputs only.

Install the optional tool dependency in an isolated environment and run (from the repository root):

```sh
python3 -m pip install -r skills/social-video-motion-design-director/code-video/requirements.txt
python3 skills/social-video-motion-design-director/code-video/tools/vector_profile.py skills/social-video-motion-design-director/code-video/examples/vector-example.json --frame 0 --output /tmp/director-frame-0.svg
python3 skills/social-video-motion-design-director/code-video/tools/qa.py skills/social-video-motion-design-director/code-video/examples/vector-example.json
python3 skills/social-video-motion-design-director/code-video/tools/measured_checks.py skills/social-video-motion-design-director/code-video/examples/measurements-example.json
python3 -B skills/social-video-motion-design-director/evals/test_code_video_profile.py
```

The `/tmp` path above is an example scratch output; choose a nonexisting path in the user's authorized workspace for persistent deliverables. Installing dependencies requires permission. Do not expose random synthetic fixtures as production evidence.
